模拟 Python 桥接及只监听本机的 Responses 端点，让真实 Codex 调用两个读图工具。
检查后续模型请求中的 `input_image` 是否逐字节对应图片，同时确认 Base64 没有进入文字。
该测试通过 `CLASSCUE_TEST_CODEX_EXECUTABLE` 显式启用，不请求真实模型、不读取真实课程。
认证 HTTP 与实际桥接链路继续由既有 `test_course_batch.py` 的 stdio 回归覆盖。

## FireRed 历史实机结果

以下记录前几轮的资源环境结果，不作为 ASR 本身损坏的结论。本轮按用户确认不再重试或修改 FireRed。

待转写媒体由 Windows 本地 TTS 合成中文语音，当时默认选择保持原已配置且已就绪的
`fireredasr2-aed` / GPU，未下载或切换模型。真实运行先出现
`system_memory/load`、`DefaultCPUAllocator: not enough memory`；
接手后重试又出现 worker 原生退出 `3221225477`（`0xC0000005`），
独立日志定位在官方模型转 BF16 的加载阶段。后一轮曾与并发启动压力测试重叠；
停止压力测试后又在独立会话 `final-quiet-asr.jsonl` 重测，仍以
`system_memory/load` 中断，分配 13,107,200 字节失败。
该次开始前可用物理内存约 7.56 GiB、可用提交空间约 6.92 GiB。
该轮不能判定真实转写成功；也不能只把失败归因于先前测试并发。

继续诊断时，曾隔离试验“逐张量转换并搬运 CUDA”以减少完整 CPU 低精度副本：
约 3,360 万参数的合成模型权重、浮点和整数缓冲区、输出一致，共享权重保留；
峰值私有提交内存从 2,256.39 MiB 降至 2,196.32 MiB，显存峰值均为 73.34 MiB。
候选改动的 132 项独立相关回归通过，但完整默认 FireRed 的独立真实任务
`transfer-asr.jsonl` 仍在 `model.to()` 中以 `0xC0000005` 退出，未生成字幕。
此次系统提交空间一度不足 1 GiB；退出码本身不等同于已证实的内存分配异常。
候选加载改动及其专用测试已经撤回，最终产品恢复先前已审核版本。
上述小模型和候选回归结果仅为诊断证据，不是最终产品新增能力或真实 ASR 通过证据。
